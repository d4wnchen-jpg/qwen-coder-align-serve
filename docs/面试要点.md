# 面试要点速记：数据 → 训练 → 评估

> 用途：面试前快速过一遍本项目的核心知识点（Q = 面试官可能的问法）。
> 范围：data / train / eval / serve（W2-W3 已实测）。

## 0. 一句话项目叙事

> 用 Magicoder-OSS-Instruct 自筛 3000 条代码指令数据，LoRA SFT 做 rank×epoch 矩阵实验，
> EvalPlus（plus 版）做 held-out 评测，实测「强基座上 SFT 负优化」的过拟合规律；
> 主线落在高吞吐部署：vLLM 0.27 下 multi-LoRA 热切换 + AWQ 量化 + prefix caching 压测，
> 全程防数据污染、可复现。

---

## 一、数据（data）

**Q: 用的什么训练数据？为什么选它？**
- Magicoder-OSS-Instruct-75K（UIUC ISE Lab 出品，MIT 许可，75K 条）
- OSS-Instruct 造数法：真实开源代码作种子 → LLM 反推题目 → 生成解答（题目真实、多样、可溯源）
- 语言分布：Python 50.9%，shell/TS/C++/Rust/PHP/Java/Swift/C# 各约 6%
- 字段：problem / solution / lang / seed

**Q: 数据怎么清洗的？（6 条规则 + 审计）**
- 空值过滤；长度过滤（instruction ≤2000，output 50~4000）
- EvalPlus 关键词粗筛（防污染）；md5 精确去重
- 代码围栏成对（防截断）；骨架解答过滤（pass/TODO 占位 ≥30% 丢弃）
- 实现题无代码过滤（instruction 要求 implement/write/create 但 output 无代码 → 丢弃）
- 产出 train 3000 / dev 200；每条规则的丢弃数落盘 `report.json` 的 filter_stats
- 独立审计脚本 `audit_quality.py`：7 类检查（围栏/骨架/拒答/截断/语言错配/无代码/重复）

**Q: 为什么训练集和评测集必须不同源？**
- 防 data contamination（背题）：同源评测 = 测记忆而非能力，分数失真
- 三层防线：①官方 decontaminated 版数据源 ②清洗时关键词粗筛 ③评测固定 plus 版
- dev（同源 200 条）管训练过程监控（loss 曲线、过拟合预警）；EvalPlus（异源）管最终能力

**Q: 数据质量怎么发现的？举一个真实案例**
- 审计发现"倒置样本"：题目里已含完整解答，输出只是文字复述（无代码）——
  这类样本会教模型"输出描述而非代码"，对 SFT 有害，已用规则过滤

## 二、训练（train）

**Q: 用什么框架？整体流程？**
- LLaMA-Factory（HuggingFace Trainer + PEFT 的上层封装）
- 流水线：读 yaml → 加载基座模型 → 套模板+tokenize 数据 → 训练 → 保存 adapter
- yaml = 配方单：一次实验一个文件，可复现、可进 git、改两个数字就是新实验

**Q: LoRA 是什么？为什么用它而不是全参微调？**
- 冻结基座，只训练低秩补丁矩阵 A/B（rank 控制补丁参数量）
- 8B 全参训练显存爆炸；LoRA adapter 仅几十 MB，4090 可训
- QLoRA = 量化底座 + LoRA；本项目最终用 bf16 全精度 LoRA + sdpa（详见「五、训练实战」）
- LoRA 可推理时动态挂载 → 正是 W5 multi-LoRA 热切换的原理（训练产物直接复用）

**Q: 训练超参为什么这么设？**
- lora_rank 16/64 × epoch 2/3 做矩阵实验（对照变量，选出最优）
- lr 2e-4 + cosine 调度 + 10% warmup（稳定起步、后期收敛）
- batch 1×grad_accum 16 = 等效 16（单步 batch 小省显存）；cutoff_len 1536（数据 p99 仅 852 token，全覆盖）；`flash_attn: sdpa`
- val_size 5% 每 200 步验证一次（防过拟合仪表盘）；bf16 训练（4090 原生支持）

**Q: yaml 里的参数是怎么"生效"的？（配置系统原理）**
- yaml 键 → LLaMA-Factory 的 dataclass 字段（声明处）→ PEFT 的 LoraConfig（消费处）→ 真插入 A/B 矩阵
- 键未声明：程序报错退出（防拼写错误）；声明但无人消费：静默失效（最阴的坑）
- 验证参数是否生效：grep 源码第二处引用，或改极端值看行为是否变化

## 三、评估（eval）

**Q: EvalPlus 是什么？**
- UIUC ISE Lab 的开源代码评测框架（NeurIPS 2023）；与 Magicoder 同实验室
- 三件套：题目集（HumanEval+ 164 题 / MBPP+ ~400 题）、加强测试用例、评分器（pass@1）
- 项目里两个角色：出卷人（evalplus.data 取题）+ 阅卷人（evalplus.evaluate 评分）

**Q: 常说的"HumanEval+ 测试用例 80 倍"是什么？**
- 原版 HumanEval 平均 ~7.7 用例/题 → + 版自动扩充到平均 ~616 用例/题（约 80 倍）
- 扩充的全是边界输入（空列表/负数/极值），几乎不存在于任何训练语料
- 效果：背题模型的分数原形毕露（原版高分 → plus 版掉 10-20 分）

**Q: pass@1 是什么？为什么 temperature=0？**
- 每题生成 1 次，通过全部测试用例才算过，通过率 = pass@1（最严格口径）
- temperature=0 贪心解码：结果确定、可复现、与公开模型分数可比
- pass@k（每题生成 k 次取最优）更宽松，项目统一用 pass@1

**Q: 生成+评分的脚本逻辑？**
- load_prompts：从 evalplus 取题，统一成 {task_id, prompt, entry_point}
- main：逐题 POST /v1/chat/completions（OpenAI 兼容协议）→ 剥 markdown 壳 → 写
  {task_id, solution} jsonl → 喂 evalplus.evaluate 评分
- 注意：HumanEval+ 是"半截函数续写"式，与训练数据"完整题面→完整解答"形式不同
  ——训练按产品形态，评测按行业统一考卷，分数才有可比性

**Q: 为什么用 argparse？**
- 一个脚本多套跑法（temperature/num-shots/out 等旋钮），改命令行不改代码
- add_argument = 声明参数（名字/类型/默认值），parse_args = 读命令行装进 args

3. 评测固定 plus 版（80× 用例，背题无处遁形）

## 四、部署与压测（serve，W2 实测）

**Q: 部署/压测做了什么？遇到了哪些坑？**
- vLLM 0.27.1 部署 Qwen3-8B（OpenAI 兼容接口），跑吞吐基线 + EvalPlus 基线
- 撞上 8 个版本坑（详见执行计划）：模型命名规则、`hf` CLI、Xet 存储、`bench latency` 改名、
  `--backend vllm` 走内部接口 404、`--endpoint` 拼接、tokenizer 加载、`--output-json` 改名
- 排查方法（可讲）：`--help` 核对参数 + curl 分步诊断 + 读源码 `api_url = base_url + endpoint`
- 核心认知：vLLM 一年发 20+ 版本，API 半年就变样——"适配最新推理框架"是 infra 岗日常

**Q: 思考模型做代码评测要注意什么？（踩过的真坑）**
- Qwen3 是思考模型，默认输出 `<think>推理</think>` 块，1024 token 全被推理占满、代码被截断 → 分数归零
- 解法：请求带 `chat_template_kwargs: {"enable_thinking": false}` + 兜底剥 `<think>`
- 教训：小样本验证优先——3 题 1 分钟就能发现，别等 563 题 1.5h 才暴露

**Q: prefix caching 是什么？为什么代码场景能 2-5×？**
- KV cache 按 block 哈希复用，前缀命中 → 跳过 prefill（最贵的前半段）
- 代码多轮/Agent/RAG 前缀重复率高 → 收益大；无重复前缀零收益；占显存 + 哈希有小开销
- 压测要做干净对照组：base 组显式关掉，对比组再开

**Q: prefix caching 实测收益多少？（W5 核心数据，面试必讲）**
- 单变量对照（同模型/同数据/同 RPS，唯一差缓存开关），高负载 RPS=32 下：

| 指标 | 关缓存 | 开缓存 | 提升 |
|---|---|---|---|
| 输出吞吐 tok/s | 1157 | 1853 | **+60%** |
| TTFT 中位 ms | 10395 | 3887 | **↓63%** |
| TTFT P99 ms | 20935 | 8415 | ↓60% |

- 两个关键实验设计点：
  1. **高负载才测得出吞吐收益**：RPS=8 时 GPU 空闲（峰值并发 47），吞吐几乎不涨；RPS=32 GPU 饱和（峰值并发 260），吞吐 +60%。教训——压测要把 GPU 喂饱，否则测的是「空闲时的延迟」不是「真实上限」
  2. **两组峰值并发必须对齐**（都是 260），TTFT 才能公平比——否则又被排队效应污染
- **为什么没到 2-5×**：数据集前缀仅 256 token（占输入一半）；前缀占比越高收益越大，真实 Agent 长 system prompt 前缀占 70-90% 时收益逼近 2×
- 关键认知：**prefix caching 收益 = f(前缀占比, 负载强度)**，两个变量决定收益量级

**Q: 压测指标都看什么？**
- 输出吞吐 tok/s、TTFT（首 token 延迟）、TPOT（每 token 延迟）、RPS
- 基线（4090，openai-chat 后端，随机数据）：输出吞吐 1290.84 tok/s

**Q: 投机解码是什么？你试过吗？（W5 实测，含负结果）**
- 原理：用草稿模型（或 ngram）先猜几个 token，主模型一次验证，猜对省时间、猜错回退
- 我试过 ngram 投机解码，**在代码场景实测负优化 -24%**（1290→979 tok/s）
- 根因两条：①ngram 在 vLLM 0.27 不支持 V2 Model Runner，强制回退 V1（性能基线低）；②代码 token 规律性弱，**接受率仅 47%**（逐位置 62%→38% 衰减，越猜越不准）
- **判断力体现**：测完发现负优化，果断放弃，而不是硬吹「用了投机解码」。最终优化选 prefix caching(+60%) + AWQ(+48%) 这两个更稳的
- 可展开：EAGLE3 收益高（1.5-2×）但需 draft 权重、与 base 强耦合、易踩坑；MTP 需模型原生支持（Qwen3-8B 无）；ngram 零成本但代码场景收益差

## 五、训练实战（W3，最有价值的面试故事）

**Q: 训练 OOM 是怎么一步步排查解决的？（重点讲这个）**
- 8B bf16 全精度 LoRA 在 4090 上贴边：显存 97%，软 OOM（PyTorch 释放缓存重试但随时可能硬崩）
- 排查链：batch 2→1（还不够）→ 想截断 cutoff → **先 tokenize 统计长度分布**，发现数据 p99 才 852 token、最大 1305 → 截断是无效操作
- 真正解法：`flash_attn: sdpa`（省注意力显存 ~4GB）+ `gradient_checkpointing` + batch 1
- 结果：显存 97% → 78%，稳定
- **核心教训：调参前先看数据**。之前绕了 batch/cutoff 一大圈，根因是"底座 16.4GB 该省注意力显存"，一刀 sdpa 解决

**Q: flash-attn 为什么装不上？sdpa 是什么？**
- flash-attn 需要源码编译，torch 2.13 + CUDA 13 太新没有预编译轮子 → 编译失败
- sdpa = PyTorch 内置的 SDPA 注意力（torch 自带、免安装），比 eager 省显存、接近 FA2 效果

**Q: LoRA 的 rank 和 alpha 是什么关系？**
- ΔW = B×A，rank 是中间瓶颈维度（补丁大小）；更新量乘 `alpha/rank`
- 惯例 alpha=2×rank → 缩放系数恒为 2，4 组实验比的是"补丁大小"单变量

**Q: LLaMA-Factory 数据怎么接入？**
- `data/dataset_info.json` 注册（`columns` 映射 + `formatting: alpaca`）
- yaml 里 `dataset: code_train` 引用注册名；LLaMA-Factory 默认 dataset_dir=data

**Q: 训练脚本的工程细节（踩过的坑）**
- `set -e` 失败即停（缺了它，OOM 后脚本还"假完成"继续跑下一组）
- 锁文件防重复启动（重复启动两个实例抢同一块 GPU → 双双 OOM）
- 长任务一律 `nohup ... &`（终端断了任务不断）

**Q: 训练矩阵结果如何？怎么选最优 checkpoint？（最核心的面试故事）**
- 4 组实验（r16/64 × e2/3）loss vs 评测分数成反比，完整数据：

| 模型 | 训练loss | HumanEval+ | MBPP+ |
|---|---|---|---|
| 基线 Qwen3-8B | — | **81.1%** | 61.7% |
| r16-e2 | 0.2299 | 73.2% | 62.9% |
| r16-e3 | 0.1506 | 71.3% | 60.2% |
| r64-e2 | 0.1683 | 75.6% | 61.2% |
| r64-e3 | **0.0644** | 70.7% | 60.7% |

- **结论：4 组 SFT 全部跑输基线**，最优 r64-e2（75.6%）仍落后基线 5.5 分
- **过拟合铁证**：loss 越低 HumanEval+ 掉越狠——r64-e3 loss 最低（0.0644）却垫底（-10.4），r64-e2 loss 中等反而最好
- **选 checkpoint 的正确姿势**：用 held-out 评测（EvalPlus+）选最优，而不是信训练 loss。这是整个矩阵实验最大的方法论收获

**Q: 为什么 SFT 在强基座上会负优化？（负结果根因）**
- Qwen3-8B 本身代码能力已 SOTA（HumanEval+ 81.1%），在它上面用 3000 条教辅数据做普通 SFT
- 结果不是提升而是**灾难性遗忘 + 风格漂移**：学会模仿 Magicoder 写法，丢掉自身强泛化
- rank 越大越易过拟合（r64 两组在 e3 暴跌）；MBPP+ 全部在基线 ±1 内，印证「没学到真能力，只是死记」
- **这个负结果是加分项不是减分项**：完整证据链（held-out 选型 + 防过拟合 + rank 敏感度）比一个平庸的正结果更能讲

**Q: SFT 负优化了怎么补救？（补救谱系 + 取舍判断，被追问必答）**
- 先定位根因：**强基座 + 弱教辅数据 + 过拟合**，不是 LoRA 技术本身问题
- 三层补救谱系，按「能翻盘吗」排序：

| 方案 | 能翻盘吗 | 成本 | 判断 |
|---|---|---|---|
| 数据掺杂（混通用数据防遗忘）| ❌ 只能止损 | 低 | 能少退 1-2 分，超不回基线 |
| 调 LoRA 超参（更低 rank/lr/早停）| ❌ 只能止血 | 低 | **矩阵已证伪**：r16-e2 最保守仍输 8 分 |
| DPO/GRPO（可验证 reward 教正确性）| ✅ 唯一可能翻盘 | 高（超出预算）| 是独立项目不是补救 |

- **为什么不再调 LoRA 参数**：r16/r64 × e2/e3 矩阵已覆盖两个最关键变量，结果「两个极端都输基线」（过拟合论下 r16-e2 该最好→73.2%，欠拟合论下 r64-e3 该最好→70.7%），证明是「强基座+弱数据」根本矛盾，不是超参问题。再调 r=8/lr 只是在 70-76% 区间挪 1-2 分，烧卡时 ROI 极低
- **代码场景的 RL 关键洞察（加分点）**：代码任务有**免费、客观、可自动验证的 reward**（测试用例通过/失败），这正是 DeepSeek-R1/GRPO 那套「可验证 reward」在代码上的应用。SFT 教「像 Magicoder 那样写」，RL 教「写出能跑通的代码」——后者才是 HumanEval+ 真正测的
- **最终取舍话术**：定位根因 → 矩阵排除超参论 → 知道完整解法谱系 → 基于成本收益如实记为负结果、主线转 serving。展示「会定位、会排除变量、会做权衡」三层能力

**Q: DPO 有可行性吗？现成数据能用吗？**
- DPO 技术上可行（LLaMA-Factory 原生支持），但**瓶颈是偏好对数据**，有两条路：
  - 途径 A（代码场景最优）：用**可验证 reward** 自动造偏好对——让模型生成 N 个解答，测试通过=chosen、失败=rejected。免费、客观，但这已半只脚踩进 RL，DPO 只是训练算法
  - 途径 B：LLM-as-a-judge 或人工标注「哪个更好」——代码场景主观、成本高、质量不可控
- **现成代码 DPO 数据集是存在的**（如 CodeUltraFeedback，coseal/CodeUltraFeedback，LLM-as-a-judge 打分 ~10K 条），但要注意**口径错配**：它们的「偏好」多是「哪个更符合人类风格/可读性」，不是「哪个能通过测试」。直接拿来做 DPO，教的是风格偏好而非正确性，未必能救 HumanEval+
- 结论：现成数据「有但不对口」，真正对口的是自己用测试通过率造偏好对——而那已经是独立项目量级

## 六、量化 + Multi-LoRA 部署（W4，本轮新踩）

**Q: 量化是为了提高效果吗？（概念澄清）**
- 不是。量化是**用「一点效果损失」换「大幅降低部署成本」**，优化的是部署性价比不是模型聪明度
- bf16 → AWQ INT4：权重 16bit→~4bit，显存 16GB→~5GB，效果通常掉 1-3 分，吞吐反而上升（更大 batch）
- 为什么有价值：正是这个 tradeoff 值得做实验——「掉几分？省多少显存？吞吐涨多少？」三组数字对比 = serving 报告核心表格
- 选型话术：AWQ 省得多但掉分多，FP8 掉分少但省得少——能讲出 tradeoff 就是加分

**Q: Multi-LoRA 是什么？为什么一个基座能挂 N 个？**
- LoRA 本质 = 冻结主模型 + 每个 adapter 只存低秩增量矩阵（ΔW=B×A）
- 挂 N 个 adapter：主模型权重只加载一次（16.7GB 固定），每个 adapter 只额外占几十~几百 MB（rank16≈175MB，rank64≈698MB），4 个加起来零头
- 请求靠 `"model": "r64-e2"` 路由到对应 adapter，运行时热切换，不用重启
- `--max-loras` 是「同时活跃的 adapter 上限」，`--max-lora-rank` 是「允许的最大 rank」

**Q: 挂多个 LoRA 会拖慢推理吗？（W5 实测数据）**
- 实测（RPS=8，同服务挂 4 个 adapter）：

| 场景 | 吞吐 tok/s | 相对 |
|---|---|---|
| 纯基座 bf16 | 1290 | 基准 |
| 挂 1 个 LoRA | 1124 | -13%（ΔW 矩阵乘法固定成本）|
| 挂 4 个 LoRA 轮询 | 1068 | 再 -5%（≈噪声）|

- **核心结论：adapter 数量不是瓶颈**。挂 4 个 ≈ 挂 1 个（-5% 是波动），因为所有 adapter 常驻显存、路由只是选指针，没有「切换」动作
- 一句话卖点：**1 份基座显存（16.7G）白赚 N 个领域能力，代价只有 LoRA 本身的 ~13%**
- 三段 tradeoff 全景：挂 LoRA -13% / adapter 数量无额外开销 / AWQ +48%（量化提速）

**Q: vLLM 0.27 挂 Multi-LoRA 踩了什么坑？（真坑，可讲）**
- 脚本循环拼了 4 个 `--lora-modules name=path` → 服务起来 `/v1/models` 只剩 1 个 adapter
- 日志第一条：`Found duplicate keys --lora-modules`，argparse 只保留最后一个
- 排查：`EngineArgs` 里根本没有 `lora_modules` 字段（是 serve 层专属参数），用 `make_arg_parser` 看 action，发现 `nargs='+'` + `LoRAParserAction`（不是 append）
- 解法：**一个 `--lora-modules` 后面接多个值**（空格分隔），不能重复写 flag
- 方法论：查参数用 `python -c "import ...; make_arg_parser(p)"` 看 `nargs`/`action class`，比翻文档快且准

**Q: vLLM 挂 LLaMA-Factory 的 adapter 要确认什么？**
- adapter 目录只要 `adapter_config.json` + `adapter_model.safetensors`（checkpoint-xxx/ 是训练中间产物，推理不用）
- 关键看 `adapter_config.json`：`base_model_name_or_path` 必须是本地绝对路径（否则 vLLM 又去 hub 找）、`r` 值要 ≤ `--max-lora-rank`、`target_modules` 是标准 PEFT 字段
- 本项目无需 export 合并模型：训练直接产出的 adapter 就能挂 vLLM，省 16GB 磁盘 + 一步导出

**Q: 磁盘满了（os error 28）怎么排查？**
- `du -sh /path/* | sort -rh | head` 找大户，而不是乱删
- 本次元凶：失败的 export 半成品（14G，写一半被掐断）+ 下载残留缓存 hf_cache（5.3G），删掉即释放 19G
- 教训：export 合并模型写 16GB 前先算清磁盘余量；半成品目录（safetensors 分片不全）是典型残留

**Q: AWQ 量化的实测 tradeoff 数据？（W4 核心成果）**
- 干净对照（同脚本、同服务参数、同关思考方式，只差 quantization）：

| 指标 | bf16 基线 | AWQ INT4 | 变化 |
|---|---|---|---|
| 权重显存 | 16.72 GiB | 5.71 GiB | **省 66%** |
| KV cache 可用 | 3.99 GiB | 14.0 GiB | **多 3.5 倍** |
| HumanEval+ | 81.1% | 74.4% | ↓ 6.7 |
| MBPP+ | 61.2% | 60.9% | ↓ 0.3 |

- **掉分不对称**：HumanEval+（极值/边界用例）对量化噪声敏感掉 6.7 分；MBPP+ 几乎不损失（0.3）
- **选型结论（面试必讲）**：部署要极致显存/高并发 → AWQ 值；代码质量优先 → bf16 更稳。能讲出这个 tradeoff = serving 岗加分
- 方法论：**评测口径一致性比分数本身重要**——早期 81.1% 和干净重测 81.1% 分数相同但输出风格迥异（关思考 vs 剥壳兜底），量化对比必须用同口径重跑，否则掉分数据不成立
